# Web services

**Cíl:** Jak propojit různé aplikace
- napsané v různých jazycích
- nasazené na různých platformách
- vyvíjené různými týmy

### Definice (W3C)

- **Web service (webová služba):** softwarový systém pro interoperabilní strojovou komunikaci přes síť
- **Rozhraní** popsáno strojově zpracovatelným formátem (např. **WSDL**)
- Interakce pomocí **SOAP** zpráv, obvykle přes **HTTP** s **XML** serializací
- Pozn.: W3C definice je omezená na SOAP – existují i jiné typy webových služeb (např. REST/JSON)

### Principy a vlastnosti

- Používá **standardizované otevřené protokoly** (HTTP, SOAP)
- Používá **otevřené datové formáty** (XML, JSON)
- **Nezávislost na technologickém stacku** poskytovatele i klienta
- Komunikace mezi **Requester** (žadatel) a **Provider** (poskytovatel) podle dohodnuté WS specifikace (formát + sémantika)
- Role **Agent** – software schopný posílat a/nebo přijímat zprávy
- Web service je často „černá skříňka“ – uživatel nevidí implementaci
- Většinou **stateless** → jednodušší návrh, lepší škálovatelnost

### Realizace

- Jeden webservice může mít více realizací (různí agenti v různých jazycích)
- Typický tok: provider zpřístupní službu → requester ji objeví → dohodnou se na používání

### Použití (Use cases)

- **Znovupoužitelné komponenty**
	- **Autentizace uživatelů**
	- **Počasí (weather forecast)**
	- **Převod měn (currency conversion)**
	- **Navigace**
- Propojení stávajícího softwaru nezávisle na programovacím jazyce a platformě (Unix, Windows, Raspberry PI)

# Representational State Transfer (REST)

- **Architektonický vzor** pro návrh webových služeb
- **Není protokol** — soubor doporučení pro navrhování API
- **Cíl:** vytvářet API, která jsou snadno použitelná

### Orientace na zdroje (resource)

- Zdroje identifikované URI (např. [http://www.blogysek.com/authors](http://www.blogysek.com/authors))
- Struktura jako adresář:
    - /authors — _všichni autoři_
    - /authors/{id} — _jeden autor_
    - /authors/{id}/articles — _články patřící autorovi_

### Explicitní použití HTTP metod

- Endpoints příklady: /posts, /users, /categories
- Metody: **GET, POST, PUT, DELETE, PATCH, OPTIONS**

### HTTP operace (příklady)

- **GET — čtení**
    - GET /posts → 200 OK + data
    - GET /posts?author="Duelling Cavalier" → dotazování (query)
- **DELETE — odstranění**
    - DELETE /posts/12 → 204 No Content
- **POST — vytvoření/aktualizace**
    - POST /posts/ → 201 Created, Location: /posts/{id}
    - Často když server generuje ID (neznáme lokaci)
- **PUT — vytvoření/aktualizace**
    - PUT /posts/12 → 201 Created, Location: /posts/12
    - Použít když známe přesnou lokaci
    - **Idempotentní**: opakovaný stejný požadavek → stejný výsledek
- **PATCH — částečná modifikace**
    - PATCH /posts/12 { "createdBy": "Gene Kelly" } → 200 OK
- **OPTIONS — seznam povolených metod**
    - OPTIONS /posts → Allow: HEAD, GET, DELETE, OPTIONS

### PUT vs POST

- POST: když neznáme lokaci nebo server generuje nové zdroje; není idempotentní (opakované volání může vytvořit více zdrojů)
- PUT: když známe lokaci; idempotentní (opakované volání stejného stavu)

### Když potřebujete jméno metody v URI

- Použití pro složité dotazy/formuláře (např. pokročilé vyhledávání):
- **POST /posts/queries** nebo **POST /posts/forms/search**

### Formát dat

- Jakýkoli standardní serializační formát: **JSON, XML, YAML**
- Poznámka: **JSON** obvykle zabírá méně místa než XML

### HATEOAS (Hypertext As The Engine Of Application State)

Používání hypertextových odkazů v odpovědích, aby klient mohl procházet API bez pevného zakódování struktury
- Příklad odpovědi: seznam položek + odkaz na každou

**Výhody**:
- Definovaný entry-point vrací odkazy → volná vazba mezi klientem a serverem

**Nevýhody**:
- Obtížné správně implementovat; méně vývojářů to umí
- Více požadavků pro procházení API
	- lze částečně vyřešit pomocí HTTP cache (If-Modified-Since)

### Shrnutí návrhu REST

- Directory-like, resource-oriented endpointy
- Použití HTTP metod pro operace → **konzistentní vzhled API**
- Nemusíte dodržet všechny pokyny, aby bylo API použitelné
- Dobrá REST návrh řeší:
    - **Verzování**, **evoluce API**
    - **Výkon** (cache)
- Rizika při špatném návrhu:
    - Prolomení oddělení klienta a serveru (tight coupling)

### Nevýhody a omezení REST

- Není univerzální řešení (není "stříbrná kulka")
- Nutnost předem rozhodnout use-cases API
- Možnost **over-fetching / under-fetching** (stahování přebytku/nedostatku dat)
- Obtížnost správné implementace a použití — může být těžké jej navrhnout i využít

# GraphQL

- **API query language (a runtime)**
- Řeší problémy tradičního REST:
    - **Over‑fetching** a **under‑fetching**
    - **Silný typový systém (strong type system)**
    - Rychlý vývoj a evoluce API

### Příklad typové definice

- `type Query { me: User }`
- `type User { id: ID name: String }`

**Požadavek** — `{ me { name } }`

**Odpověď** — `{ "me": { "name": "Luke Skywalker"} }`

### Typ (type)

- Definice objektu, který lze získat ze služby
- Příklad:
    - `type Character { name: String! appearsIn: [Episode!]! }`

## Argumenty polí

- Každé pole může mít argumenty
- Příklad:
    - `type Starship { id: ID! name: String! length(unit: LengthUnit = METER): Float }`

## Query — vstupní bod pro čtení dat

- Definuje, jaké dotazy lze volat
- Příklad:
    - `type Query { hero(episode: Episode): Character droid(id: ID!): Droid }`
- Příklad dotazu:
    - `query { hero(episode: NEW_HOPE) { name } }`
- Příklad odpovědi:
    - `{ "data": { "hero": { "name": "R2‑D2" } } }`

## Mutation — vstupní bod pro změny

- Definuje operace měnící stav
- Příklad:
    - `type Mutation { login(email: String): String }`
- Příklad mutation:
    - `mutation { login(email: "jakub.danek@yoso.fi") }`
- Odpověď:
    - `{ "data": { "login": "<token>" } }`

## Operace s názvem a proměnné

- Příklad pojmenované mutation s proměnnou:
    - `mutation SignIn($email: String) { login(email: $email) }`
    - `variables: { "email": "jakub.danek@yoso.fi" }`

## GraphQL přes HTTP

- Jediný endpoint (např. /graphql)
- Metody:
    - **GET** /graphql?query={me{name}}
    - **POST**: JSON tělo `{ "query": "...", "operationName": "...", "variables": { ... } }`
- Odpověď:
    - `{ "data": { ... }, "errors": [ ... ] }`

## Výhody GraphQL

- Klienti definují, co potřebují — **není nutné navrhovat API podle všech klientských use‑case**
- **Žádný over‑ nebo under‑fetching** (minimálně na HTTP vrstvě, obvykle ne na DB)
- Snadné na pochopení a rychlý vývoj

## Nevýhody GraphQL

- Horší škálovatelnost v některých scénářích
- Obtížné cachování — často nutné implementovat case‑by‑case
- Pouze JSON reprezentace
- Těsné provázání serveru a klienta (tight coupling)
- Často znamená znovuvynalézání některých HTTP mechanismů

## Kdy zvolit GraphQL vs REST

GraphQL
- Rychle se vyvíjející aplikace bez silné potřeby server‑řízeného stavu

REST
- Distribuovaný systém s potřebou kontroly stavu na serveru
- Vysoké požadavky na škálovatelnost a výkon

# Simple Object Access Protocol (SOAP)

- **Co to je:** XML-based messaging protocol
- **Funkce:** zprávový protokol, definice formátu zpráv a pravidel kódování datových typů
- **Klíčové vlastnosti:** všechny zprávy v XML; akce určeny obsahem zprávy

### Struktura SOAP zprávy

- **Envelope** — obálka zprávy (kořenový element)
- **Header** — volitelný; způsob rozšíření protokolu (např. bezpečnost, metadata)
- **Body** — hlavní XML element obsahující data zprávy
- **Fault** — informace generované při chybě

Příklad formy:

```xml
<env:Envelope xmlns:env="http://www.w3.org/2003/05/soap-envelope">
	<env:Fault>
	...
	</env:Fault>
	<env:Header>
	...
	</env:Header>
	<env:Body>
	...
	</env:Body>
</env:Envelope>
```

### Výhody

- **Flexibilní**
- **Rozšiřitelný**
- Používá **XML** → podporuje XSD, internacionalizaci, jmenné prostory (namespaces)

### Nevýhody

- **Žádný standardizovaný přístup k návrhu API**
- Používá **XML** → rychle roste velikost a složitost zpráv → možné problémy s výkonem

### Příklad požadavku (souhrn)

- HTTP POST na /InStock s Content-Type: application/soap+xml
- SOAP Envelope obsahuje Body s operací GetStockPrice a parametrem StockName (např. IBM)

### Příklad odpovědi (souhrn)

- HTTP 200 OK s Content-Type: application/soap+xml
- SOAP Envelope obsahuje Body s GetStockPriceResponse a elementem Price (např. 34.5)

## WSDL (Web Services Description Language)

- **Co to je:** XML schema pro popis webových služeb (nejen u SOAP, ale často používané spolu se SOAP)
- **Účel:** popis typů, operací a vazeb služby; umožňuje generování klientského kódu

### Hlavní elementy WSDL

- **\<types>** — definuje datové typy použitím XML Schema (XSD)
- **\<message>** — definuje datové elementy pro každou operaci
- **\<portType>** — definuje operace služby a související zprávy (input, output, fault)
- **\<binding>** — spojuje portType s konkrétním protokolem (např. SOAP)
