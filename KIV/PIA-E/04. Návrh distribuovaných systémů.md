# Návrh distribuovaných systémů

**Proč je to těžké**
- síťová latence (network latency)
- závislostní peklo v microservice architektuře (dependency hell)
- služby mohou být dočasně nedostupné
- udržení konzistence dat napříč systémy

### Komunikační styly

- **Synchronous (synchronní)**
    
    - vždy one-to-one
    - blokující request-response (webservice, databáze)
    - obvykle těsné provázání (tight-coupling)
    - problém: pokud cílová služba není dostupná, proces selže
- **Asynchronous (asynchronní)**
    
    - one-to-one i one-to-many (publish-subscribe)
    - asynchronní request-response, notifikace (point-to-point messaging)
    - lepší odolnost vůči dočasné nedostupnosti služeb
    - umožňuje eventual consistency (systém se dospěje ke konzistentnímu stavu později)

### Topologie komunikace

**Brokerless**
- může být synchronní i asynchronní
- žádná další komponenta v systému
- služby se musí navzájem najít (service discovery)

**Broker-based (message broker)**
- musí být asynchronní (messaging je vždy asynchronní)
- broker může být single point of failure nebo úzké místo výkonu
	- většina brokerů má ale vysokou škálovatelnost/HA
- broker slouží jako rozhraní mezi službami → loose coupling
- broker funguje jako buffer (uloží zprávy, dokud je služba nezpracuje)
    - nutí návrh tolerovat dočasnou nedostupnost služeb

### Message broker — příklady a protokoly

- Příklady: Apache ActiveMQ/Artemis, RabbitMQ, Apache Kafka, AWS SQS, Azure Service Bus, Redis
- Komunikační protokoly: **AMQP**, **MQTT**, **STOMP**
- Poznámka: JMS není protokol, ale Java API pro messaging

### Zlepšení dostupnosti přes messaging

- Více synchronních závislostí snižuje celkovou dostupnost (např. 0.95^3 pro 3 služby)
- Asynchronní komunikace zvyšuje dostupnost — služby nemusí být dostupné v okamžiku události
- Systém dosahuje konzistence eventuálně
- Otázka: (distribuované) transakce — potřeba řešit

### Řešení duplicitních zpráv

- Problém: selhání klienta/brokera/sítě může vést k opakované doručení (většina brokerů garantuje alespoň jednou)
- Řešení A — idempotentní consumer logic
    - opakované zpracování téže zprávy nemění stav
    - není vždy možné
- Řešení B — sledování zpracovaných zpráv přes unikátní ID

### Service Discovery (objevování služeb)

- Problém: dynamické škálování znemožňuje statickou konfiguraci IP → potřeba service registry
- Možnosti:
    - (a) **reverse proxy / load-balancing reverse proxy**
        - vyžaduje externí tooling pro aktualizaci konfigurace proxy při start/stop replik
        - proxy musí podporovat seamless reloads (např. HAProxy)
        - snadné nastavení, ale nevhodné pro dynamické nasazení
    - (b) **external service registry**
        - služby (nebo orchestrátor) zapisují záznam přes Registration API při startu
        - klienti dotazují aktuální adresy replik podle potřeby
        - discovery protokoly: HTTP, DNS, …
        - příklady: Netflix Eureka, HashiCorp Consul, SkyDNS
        - přidává další komponentu do systému a komplikuje klientský kód; zvaž knihovnu pro daný jazyk/framework
    - (c) **platform-based discovery**
        - registry nabízejí nasazovací platformy (Kubernetes, OpenShift, AWS, Azure)
        - klienti volají doménu služby → router rozpozná službu a směruje požadavek
        - platforma transparentně spravuje registraci a discovery (server-side discovery)
        - funguje jen pro služby nasazené na dané platformě/clusteru

### Service Discovery — poznámky k reverse proxy

- Proces při startu repliky:
    - nová replika startuje → IP přidána do konfigurace proxy → konfigurace reloadována
- Nevýhoda: potřeba externího nástroje pro update konfigurace
- Doporučení: nepoužívat pro velmi dynamická nasazení

### Use-cases — kdy synchronní vs. asynchronní

- **Synchronní vhodné pro**: validace dat při vytvoření objednávky (tam, kde potřebujete okamžitou odpověď)
- **Asynchronní vhodné pro**: zpracování plateb, změna stavu objednávky (event-driven), notifikace klienta (SMS, email, push), hromadné importy uživatelů, přidání elektronického razítka do dokumentu

### Shrnutí

- Preferovat asynchronní messaging tam, kde škálovatelnost a dostupnost důležitější než okamžitá konzistence
- Dohlédnout na idempotenci nebo tracking zpráv kvůli duplicitám
- Pro service discovery zvolit řešení odpovídající míře dynamiky deploymentu:
    - statické/nízká dynamika → reverse proxy může stačit
    - dynamické škálování → registry nebo platform-based discovery
- Používat robustní brokery/protokoly a knihovny dostupné pro váš stack
