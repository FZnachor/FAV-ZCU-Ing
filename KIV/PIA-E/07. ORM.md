## Object‑Relational Mapping (ORM)

**Problém:** Boilerplate kód při práci s JDBC (ruční PreparedStatement, ResultSet → převod do objektů)

**Cíl ORM:** Zjednodušit práci — místo SQL volání repository.metoda (např. repository.findAll(User.class))

### Co je ORM?

- **Most** mezi objektovým světem a relační databází
- **Typické mapování:** třída → tabulka, atribut → sloupec
- **Co ORM zajišťuje:** mapování řádků na instance, dotazů na metody; vývojář běžně nepíše SQL

### Co ORM není (omezení)

- **Není stříbrná kulka (silver bullet)** — vždy zvažte use case
- **Není dokonalá abstrakce** nad relační DB
- **Rizika:** výkonové problémy, komplikace při vývoji softwaru, režie mapovací logiky

### Kategorie ORM

- **Plně automatické (Automatic ORM)**
    - Generují SQL automaticky (vývojář nepiše SQL)
    - Snadné používat, těžké používat správně
    - Příklady: _Hibernate_, _EclipseLink_ (implementace JPA)
- **„Manuální“ ORM (Manual ORM)**
    - Vývojář stále píše SQL, framework pomáhá s mapováním (řádky → instance)
    - Příklad: _MyBatis_

### Příklady

- JDBC (ruční):
    - PreparedStatement, ResultSet, smyčka vytvářející objekty
- Automatické (JPA):
    - @Entity, @Table, @Id, @Column; repository.persist(user), repository.find(1L, User.class)
- Manuální (MyBatis):
    - Interface s @Select, @Insert, @Results mapováním sloupců na vlastnosti

### Impedance mismatch (nesoulad modelů)

**Důvod:** objektový a relační model nejsou totožné

**Dopady:**
- Ovládání přístupu (private fields) — často nutné veřejné get/set; moderní implementace umožňují mapování privátních polí
- Dědičnost — různé strategie:
	- Table per class (tabulka za každou třídu)
	- Single table (vše v jedné tabulce → mnoho prázdných sloupců)
	- Joined tables (superclass tabulka + podtřídy → více JOINů, dopad na výkon)
- Relace (association, composition, aggregation) — v paměti jsou přístupy jednodušší než v SQL (nutné JOINy a spojovací tabulky)

### Výkonové problémy

- **Režie ORM:** reflexe, generování dotazů, lazy/eager logika — zpomaluje
- **N + 1 SELECT problém:**
    - 1 dotaz pro seznam N položek + N dotazů pro jejich asociace → stovky dotazů pro jednu stránku
    - Na vývojovém stroji může být OK, v produkci kolabuje
- **Řešení:**
    - **LAZY loading** pro *-to-many kolekce (default)
    - **JOIN** pro *-to-one asociace (načíst pomocí JOIN, pokud potřeba)
    - Pro *-to-many: buď separátní načítání kolekce, nebo dvě fáze — 1) načíst hlavní položky, 2) bulk načíst všechny asociace pro všechny položky a přiřadit je in‑memory
    - Vytvářet metody specifické pro načítání kolekcí tam, kde je třeba

### Obecná pravidla (Best practices)

- **THINK!**
- **Mapovat kolekce (*-to-many) vždy jako LAZY**
- **Načítat EAGER (non-lazy) *-to-one přes JOIN**
- **Neignorovat relační databázi** — nepředstíráme, že tam není (leaky abstraction)

### Důsledky používání ORM

- ORM ovlivňuje návrh aplikace:
    - datové struktury, rozhraní objektů, přístupová práva
    - návrh aplikačního rozhraní — dochází k _leaky abstraction_

### Implementace podle jazyků (přehled)

- Java: Hibernate, EclipseLink, OpenJPA, MyBatis
- Ruby: ActiveRecord, DataMapper, Sequel
- Python: Django ORM, SQLAlchemy, Peewee, SQLObject
- .NET: Entity Framework, nHibernate
