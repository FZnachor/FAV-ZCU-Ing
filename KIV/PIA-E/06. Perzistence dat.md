# Perzistence dat

### Hlavní body

- **Kde ukládat** (WHERE): RDBMS, NoSQL, souborový systém, jiné služby
- **Jak pracovat s daty** (HOW): dotazy, předávání parametrů
- **Konzistence**: transakce
- **Správa připojení**: connection pooling

## Proč řešit perzistenci

- Vliv na nefunkční požadavky:
    - **Výkon**
    - **Bezpečnost**
    - **Trvanlivost (durability)**

## Možnosti úložišť

### RDBMS

- Příklady: MariaDB, MySQL, PostgreSQL, Oracle, MS SQL Server, Derby, H2
- Vhodné pro relační data (tabulky, relace)
- Výhody:
    - Ověřené, málo chyb
    - Silná komunita a nástroje

### NoSQL

- Různé typy databází pro specifické případy
- Sdílené rysy:
    - Škálovatelnost, partitioning před konzistencí
    - Většinou eventual consistency
    - Slabší podpora transakcí, dobrá replikace
- Poznámka: NoSQL doplňuje, ne vždy nahrazuje RDBMS — volit podle požadavků

Podtypy NoSQL:

- Dokumentové (MongoDB, CouchDB)
    - Vhodné pro nestrukturovaná/stromová data, omezené relace
- Key-Value (Redis)
    - Velmi rychlé, cache, indexy
- Wide-Column (Cassandra, DynamoDB)
    - Škálovatelné, vhodné pro málo aktualizací (logy, tracking)
- Grafové (Neo4j, Giraph)
    - Výborné pro grafové dotazy (mapy, ontologie)

### Souborový systém

- Snadné použití, ale problémy při horizontálním škálování
- Omezené indexování a dotazování → nevhodné pro produkci při škálování

### Jiné možnosti

- Specializované nástroje: Alfresco (file management), ElasticSearch (full-text, analytics), Amazon S3 (objektové úložiště), objektové DB (ObjectDB)

## Modelování dat a organizace

- Struktura perzistence ovlivňuje výkon, konzistenci, prostorové nároky
- Konflikt: rychlé čtení vs. rychlé zápisy
- Důležité otázky:
    - Kolik dotazů potřebuji k získání dat?
    - Potřebuji celé záznamy nebo jen subset?

Přístupy:

- Normalizovaný model
    - Data uložená jednou → méně místa, rychlé aktualizace
    - Čtení vyžaduje JOINy → horší výkon
- Denormalizovaný / single-table (data warehouse)
    - Duplicitní předpočítaná data → rychlé čtení, pomalé aktualizace, obtížná konzistence

## Výkon přístupu k datům

- Dvě hlavní dimenze:
    1. Doba zpracování samotného dotazu
        - RDBMS: složité dotazy → pomalejší u větších objemů
        - NoSQL: jednoduché dotazy → rychlejší
        - Indexy: zrychlují čtení; příliš mnoho indexů zpomalí zápisy
    2. Počet dotazů (síla implementace)
        - SELECT N+1 problém: 1 dotaz pro seznam + N dotazů pro detaily → špatné
- Škálování pro velké objemy: měřit, navrhovat podle reálných dat (10k, 100k, 1M, 10M)
- Shrnutí: aplikace by se měla tvářit nezávisle na úložišti, ale vývojář musí znát vlastnosti úložiště pro správný návrh výkonu

## Konzistence a transakce

### Transakce

- Jednotka práce: buď vše proběhne, nebo nic (žádné částečné změny)
- ACID: **Atomicity**, **Consistency**, **Isolation**, **Durability**

### Izolace

- Snížení izolace transakcí pro zvýšení konkurence
- **Dirty reads**: čtení dat z necommitované transakce
- **Nonrepeatable reads**: opakované čtení může vrátit jiné hodnoty po commitu jiné transakce
- **Phantoms**: opakovaný dotaz vrátí jiné řádky (vložené/změněné jinou transakcí)

### Zámky

- READ lock: víc transakcí může číst; writer čeká
- WRITE lock: zamkne záznam pro ostatní (read i write)

### Izolační úrovně (SQL standard)

- **Read uncommitted**: nejlepší konkurence, nejhorší konzistence
- **Read committed**: čtení jen commitovaných dat; read lock během práce, write lock do commit/rollback
- **Repeatable read**: drží read+write zámky na vrácených záznamech do konce transakce
- **Serializable**: nejvyšší izolace — zamykání rozsahu dotazu (např. celý obsah tabulky pro SELECT *)    
- Nejčastěji dostačuje **READ_COMMITTED**, ale existují scénáře (např. dynamické generování ID na základě posledního záznamu), kde je nutná vyšší izolace nebo explicitní zámky (SELECT ... FOR UPDATE)

### Příklad problému (dynamické ID)

- Algoritmus čte poslední ID, inkrementuje, vloží nový záznam → musí proběhnout v úplné izolaci
- Řešení:
    - A: nastavit izolaci na Serializable
    - B: Repeatable Read + explicitní WRITE lock při čtení (SELECT ... FOR UPDATE)

## Správa připojení k DB (Connection Management)

### Connection pool

- Zabraňuje otevírání nového připojení pro každý request → snižuje režii
- Vhodné, pokud atributy připojení nekončí měnit per request (pokud má každý uživatel vlastní DB credentials, pool nelze použít)
- Standardní parametry:
    - Minimum connections (pool drží vždy)
    - Maximum connections
    - Timeout (uvolnění přebytečných idle připojení)
    - Check query (dotaz pro ověření validity spojení)
- Parametry ovlivňují stabilitu a výkon poolu

## Shrnutí

- Volit úložiště podle konkrétních use-case a požadavků (performance, konzistence, škálování)
- Modelovat data tak, aby vyhovovala hlavním operacím (čtení vs. zápis)
- Používat vhodné izolační úrovně a zámky pro kritické operace vyžadující konzistenci
- Nasadit connection pool s adekvátní konfigurací pro produkční provoz
