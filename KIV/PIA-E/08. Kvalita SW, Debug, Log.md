# Kvalita softwaru

### Měřitelné ukazatele

- **Počet uživatelských stížností** (nedělá to, co potřebuji)
- **Počet chyb v produkci**
- **Náklady na další vývoj** — ovlivněné architekturou
- **Náklady na údržbu** — ovlivněné dobrým procesem vývoje a testingem
- **Důraz:** rychlé zjištění zdroje problémů → debugging, logy

## Hlavní oblasti

### Validation (Validace)

- Cíl: prokázat, že aplikace dělá to, co zákazník potřebuje
- Nejlépe dosaženo: dobrým vývojovým procesem a komunikací se zákazníkem

### Verification (Verifikace)

- Cíl: ukázat, že aplikace odpovídá specifikaci
- Důraz na ni roste s velikostí systému a tempem vývoje
- Vlastnosti:
    - **Opakovatelnost**
    - Prováděna v každém kroku vývojového cyklu
    - **Automatizace**
- Složitá logika se obtížně pokrývá testy
	- **dekompozice**
	- **unit-testy**

### Testing (Testování)

- Cíl: najít chyby, pokusit se aplikaci rozbít

### Debugging (Ladění)

- Cíl: najít příčinu chybového stavu
- Relativně snadné během vývoje (debug nástroje, možnost měnit kód)
- Obtížné v produkci (žádný debugger, reálná data, "must not break stuff")

## Specifika webových aplikací

- Velmi široké spektrum aplikací se specifiky
- Časté změny
- Často multi-threaded prostředí
- Mohou čelit vyššímu zatížení (např. DoS)

## Unit testy (Jednotkové testy)

- Testují malé části kódu (psané vývojáři)
- Cíl: zajistit chování částí podle specifikace
- Vlastnosti:
    - **Nezávislé** na sobě a na zbytku aplikace
    - Ideálně jeden test suite na třídu/soubor
    - Testovat:
        - správné vstupy
        - hraniční případy (0,1,2 pro sort; corner cases)
        - špatné vstupy (error handling)
        - případy jako nullable parametry (např. List findByIds(@Nullable List ids) → vrátit prázdný list)
    - Více testů na jednu metodu
- Doporučení: **test coverage > 90%** aplikační logiky
	- Pomáhají při refaktoringu, přidávání funkcí, změnách chování
	- Postup: nejdříve napsat testy, pak změnit implementaci aby testy prošly

### Nezávislost testů — přístupy

Stubs
- Speciální testovací implementace rozhraní, vrací pevná data
- Jednoduché, ale při růstu složitější údržba

Mocks
- Konfigurovatelné objekty pro každý test-case
- Příklad: mock DAO vrací konkrétní hodnotu pro kontrolu generování ID

### Architektura pro testovatelnost

- Oddělení vrstev (Clean Architecture)
- Testovatelné vstupy jako objekty místo HTTP requestů
- Nebude zapotřebí běžící server pro unit-testy

### Shrnutí unit-testů

- Zajišťují chování podle specifikace
- Testují malé části místo celku
- Nevystačí samy o sobě (nepokryjí integrace s DB či jinými systémy)
- Relativně levné a srozumitelné při chybách

## Functional tests (Funkční testy)

- Testují požadavky na běžícím systému podle use-cases/scénářů
- Slouží také jako integrační testy (pokud jsou jednoduché)
- Pokrývají integraci s externími systémy (DB, web services)

### Testovací scénáře

- Krok-za-krokem, co má tester udělat + vstupní data
- Píšou je testeři (ne vývojáři)
- Výhoda: testeři nepotřebují hluboké technické znalosti

### Automatizované funkční testy

- Skriptované test-scenáře — levnější dlouhodobě, ale nákladné na napsání/údržbu
- UI se často mění → vyšší náklady na údržbu
- Web-service API: jednodušší (poslat request, zkontrolovat response code a body)
- Moderní WS spec. jazyky podporují generaci základních testů

### Web UI automatizace

- Výzvy: lokalizace HTML elementů
    - Xpath se na stránce snadno změní
    - ID je dobré a unikátní, ale frameworky ho mohou generovat automaticky
- Řešení: přidat vlastní atributy (např. uiTest="unique id") — udržovatelné

### Selenium

- Sada nástrojů pro browser testování
- Spustitelné proti více prohlížečům
- Možnost nahrávání dění nebo psaní testů v IDE
- Příklad testu:
    - `driver.get(baseUrl + "Prevodnik");`
    - find element by id, assert value

### Robot Framework

- Nadstavba používající key-words (čitelné, možnost vlastních slov)
- Podklad pro WebUI: Selenium

## Jiné typy testů

### Integration tests

- Ověřují komunikaci mezi dvěma systémy (např. fakturace × účetnictví)
- Nutné pro integrace, které nebývají uživatelsky spouštěné (periodické procesy)

### Performance tests

- Cíle:
    - ověřit výkon pod reálným zatížením
    - testování chování při extrémním zatížení (obnova po problému)
    - detekovat regresi výkonu v nových verzích
- Provozovat v prostředí podobném produkci

### Smoke tests

- Subset funkčních/integr. testů, které rychle ověřují základní funkčnost
- Použití: ověření úspěšného nasazení (zda aplikace reaguje)
- Běžné v produkci (nechceme spouštět plné testy)

### Usability tests

- Testují snadnost použití UI pro uživatele bez předchozího seznámení
- Metoda: nechat uživatele vykonat sadu úloh
- Výstupy: varování, pokud uživatelé nejsou schopni úkol splnit; informace o chování uživatelů

# Debugging

- **Helper prints** do konzole — snadné, ale nepořádné; dobré pro vývoj
- **Breakpoints** v IDE / debug nástroje — přerušení běhu, prohlížení stavu
- **Aplikační logy** — nutnost pro debugging v produkčním nasazení

## Debugging v IDE

- **Breakpoint** — místo, kde se pozastaví vykonávání
- **Watch** — proměnná nebo výraz sledovaný během debugování

### Základní ovládací akce

- **Step Over** — pokračovat ve vykonávání o jeden krok
- **Step Into** — vstoupit do volané funkce/metody
- **Step Out** — vystoupit z aktuální funkce/metody
- **Continue Execution** — pokračovat do dalšího breakpointu nebo konce

### Užitečné tipy

- Sledujte nejen proměnné, ale i výrazy (watch expressions)
- Procházejte stacktrace během pauzy — kontrola proměnných mimo aktuální scope
- Debugger zobrazuje typ/strukturu — zvlášť užitečné v dynamických jazycích
- Možnost vzdáleného debugování — povolit explicitně, používat pouze v kontrolovaných prostředích (bezpečnostní riziko)
- Všechny hlavní prohlížeče obsahují JavaScript debugger

### Shrnutí IDE debugování

- Velmi užitečné během vývoje
- Bezpečnostní riziko ve veřejně přístupných prostředích — **nepoužívat**

## Debugging na serveru / v produkci

- Musíte zachovat provoz služby (nesmíte službu rozbít)
- Nesmíte poškodit data
- Nelze připojit interaktivní debugger
- Chyby se přesto dostanou do produkce → **kvalitní logy jsou klíčové**

# Logování

### Typy logů

- **Application logs** — vnitřní zprávy o dění v aplikaci
    - Příklad úrovně: INFO, WARN, ERROR, DEBUG, TRACE
- **Access logs** — všechna externí volání (HTTP requests)
    - Obsah: RequestId, SessionId, hostname, path, params, headers, cookies
- **Audit logs** — sledování činností konkrétních uživatelů (co, kdo, kdy, kontext)

### Úrovně logování

- **Info** — každá úspěšně dokončená akce
- **Warn** — aplikace není v chybovém stavu, ale něco není v pořádku
- **Error** — chybové situace s dostatečnými informacemi (stack trace, data)
- **Debug** — detailní informace o průběhu (datové struktury)
- **Trace** — detailní start/stop metod, podmínky (velmi verbose)

### Log chain a citlivá data

- Kombinace access + application + audit logů dává úplný obraz
- **Citlivá data by se v application logu neměla objevovat** (logy jsou přístupné údržbě)
- Audit logy obsahující citlivá data — přístup pouze pro omezený okruh lidí

### Implementace logování

- Většina jazyků má hotové knihovny s podporou:
    - formátování, úrovně, context info, filtrování podle zdroje, různé uložiště (konzole, soubor, web-service, message queue, DB)
- Moderní stack: sběr přes message queue → indexace (elasticsearch) → prezentace (kibana / logstash)
- Agregace logů na jedno místo usnadní vyhledávání a analýzu

### Moderní přístup

- Cloudové řešení pro sběr a zpracování logů (logstash/elasticsearch/kibana)
- Audit logy: garantované doručení, vlastní testy
- Správně nastavené log-levely — logování nemá být výkonový problém
