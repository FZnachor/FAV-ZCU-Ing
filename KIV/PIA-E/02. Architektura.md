## Architektura webových aplikací

**Motivace**

- Na začátku projektů mnoho neznámých
- Správný design snižuje náklady implementace funkcí
- Náročnější přístup přináší větší šanci na úspěch
- Mnoho vývojářů potvrzuje best practices

## Základní designové principy

**Oddělení odpovědností (Separation of Concerns)**
- Různé úkoly uchovávat odděleně
- Zvýšení testovatelnosti, znovupoužitelnosti, čitelnosti
- Příklad: validace vstupu u registrace oddělená od hlavní logiky

**Princip jediné odpovědnosti (Single Responsibility Principle)**
- Třída má pouze jeden důvod ke změně
- Více odpovědností → křehký design
- Příklad: závislost na GUI knihovně nutí přebudování aplikace

**Zapouzdření (Encapsulation)**
- Zabránit přímému přístupu k internímu stavu
- Přístup přes dobře definovaná veřejná rozhraní
- Objekt má vlastní stav a kontroluje jeho změny
- Auto-gettery/settery mohou zapouzdření narušovat
- Platí i pro webové služby a aplikace

**Neopakujte se (DRY)**
- Každá znalost jedna autoritativní reprezentace
- Zahrnuje kód, DB schémata, testy, dokumentaci
- Vícenásobné reprezentace vedou k chybám při změnách
- Příklad: UML datový model → generované SQL DDL

## Inverze závislostí (Dependency Inversion)

- Přímé závislosti → pevné vazby mezi třídami
- Vyšší úrovně závislé na abstrakcích (rozhraních), ne implementacích
- Výhoda: volnější vazby, snadnější výměna implementací

### Explicitní závislosti

- Aplikace/moduly/třídy uvádí potřebné závislosti
- Možnost deklarace při instalaci, sestavování nebo v konstruktoru

## Inverze kontroly (Inversion of Control)

- Řízení toku programu mimo náš kód (např. framework)
- IoC ≠ Dependency Injection, DI je konkrétní koncept IoC

Příklad: bez IoC problémy s unikátními identifikátory plateb
- Problém u více zákazníků, kteří si generují vlastní ID
- IoC z pohledu zákazníka: ID bude generovat platební brána
- Nebo každý zákazník dostane vlastní ID space

## Injekce závislostí (Dependency Injection)

- Oddělení kódu od způsobu připojení závislostí
	- Konfigurace v kódu nebo externě (např. XML)
	- Jedno místo pro změnu závislostí

Injekce přes **konstruktor**
- Závislosti injektovány konstruktorem
- Preferováno pro povinné závislosti

Injekce přes **settery**
- Závislosti injektovány pomocí setterů
- Preferováno pro volitelné závislosti

Injekce přímo **do atributů**
- Závislosti vkládány do atributů, užitečné v testech
- Často považováno za anti-vzor (skrývá závislosti)

### Alternativa: Vyhledávání služeb (Service Lookup)

- Vševědoucí service locator vrací instance na požádání
- Stále potřeba reference na service locator

### DI vs Service Lookup

- DI využívá IoC, service lookup ne
- DI je těžší na ladění (komplikovanější implementace)
- Service lookup nutí závislost na locatoru (problém u tvorby knihoven)

## Architektury webových aplikací

- Nasazení (1..n procesů/serverů) → ovlivňuje horizontální škálování a složitost aktualizací
- Externí rozhraní aplikace → vliv na integrace
- Vývojová omezení (technologie, tým) → vliv na integraci a rozšiřitelnost

**Topologie v distribuovaných systémech**
- Většina používá **klient-server model**
- **Typy klientů**: prohlížeč, AJAX skript, SPA, server-to-server, mobilní zařízení
- **Typy serverů**: webový server, DBMS, aplikační server, message broker

**Single Page Application (SPA)**
- Jediná HTML stránka s DOM manipulací přes JavaScript
- Pouze přenos dat z/na server – rychlejší odpověď
- Oddělený vývoj – vyšší komplexita

**Thick client**
- Obsahuje vlastní logiku
- Výhoda: méně zátěže serveru
- Nevýhoda: duplikace logiky pro různé klienty

**Thin client**
- Prezentace, logika na serveru
- Výhoda: sdílená logika mezi klienty
- Nevýhoda: větší zatížení serveru

**Monolitická webová aplikace**
- Struktura: UI + serverová aplikace (WS API) + databáze
- Příklad: účetní aplikace pokrývá autentizaci, faktury, mzdy, tisk, daně, zákazníky, platby
- Výhody: jednoduché nasazení, snadné otevření v IDE, jednoduché horizontální škálování
- Nevýhody: velká codebase → nižší kvalita, pomalý start VM → pomalejší vývoj, obtížné škálování částí aplikace, vysoké koordinační náklady, pevný technologický stack

**Service-Oriented Architecture (SOA)**
- Služba jako černá skříňka s kontraktem
- Volná vazba, bezstavovost (stateless)
- Komunikace: přímé volání nebo fronty (HTTP, WebSocket, SOAP, AMQP, MQTT, STOMP)
- Zvýšená integrační složitost: síťové chyby, důvěra, šifrování, složitější debugování
- Potřeba složitějšího dev prostředí a integračních testů (kontejnery pomáhají)
- Poznámka: jednoduché rozdělení monolitu na služby přes API neřeší všechny SOA problémy

**Microservices (mikroslužby)**
- Aplikace rozdělena na malé samostatné služby (samostatné procesy)
- Princip: do one thing and do it well
- Výhody: malé služby, snadné pochopení a testování, rychlé nasazení, flexibilní škálování, nezávislé aktualizace, rozdělení týmů, heterogenní technologie
- Nevýhody: složitější nasazení/provoz, vyšší nároky na nástroje, nutnost integračních testů, složitá koordinace distrib. transakcí, vyšší náklady na zdroje

**Monolit vs mikroservisy**
- Monolit vhodný pro menší aplikace (snadný vývoj)
- Mikroservisy výhodné pro velké projekty (škálovatelnost, testování, menší komplexita)
- U jazyků bez statické typizace jsou mikroservisy často nutností

## Principy návrhu webových aplikací

**Základní princip:** oddělení odpovědností (separation of concerns) – kód aplikace rozdělen do vrstev (layers)
    
**Výhody vrstev**
- **Enkapsulace** funkcionality uvnitř vrstev
- **Komunikace přes rozhraní (interfaces)** → snazší správa a výměna částí
- **Snadnější testování** (např. nahradit MySQL MongoDB; nahradit přístup do DB mocky pro unit testy)

 **Clean Architecture (čistá architektura)**
- Základní pravidlo: závislosti směřují z vnějších vrstev dovnitř (outside → in)
- Vrsty
	- **Entities** – generická pravidla sdílená napříč systémem
	- **Use Cases** – pravidla specifická pro aplikaci, řídí tok dat do/ze entit a volání jejich funkcí
	- **Interface Adapters** – převod dat z entit/use cases do formátu pro externí systémy (UI, web service controllers, DAO/database access)
	- **Frameworks & Drivers** – externí frameworky, nástroje, databáze; jen se k nim připojujete
- Koncept lze rozšiřovat o více vrstev podle potřeby

## Vrstvy aplikace

- Realizace separation of concerns na úrovni kódu
- Závislostní cesty vedou z vnějších vrstev k vnitřním – často pomocí dependency inversion
- Umožňuje opětovné volání logiky aplikace z více částí (Web UI, mobilní aplikace, testy)

Běžné vrstvy:
- **Presentation layer**
- **Application / Business logic layer**
- **Data access layer**

Cross-cutting concerns: **security**, **transactions**, **logging**

**Data Layer**
- Jak jsou data uložena (formát) – relační schema, pravidla pro dokumenty, souborové formáty
- Mapování mezi interním formátem (DTO, entities) a storage formátem (SQL, BSON)
- Implementace čtení/zápisu (READ/WRITE)

**Business Layer**
- Realizace aplikační funkcionality
- Změna stavu entit
- Spouštění přístupu k úložišti dat

**Presentation Layer**
- Přijímá vstup od uživatele
- Volá aplikační funkce
- Zobrazuje výsledky uživateli

## Návrhové vzory webových aplikací

**Model-View-Controller (MVC)**
- **Model** = data a aplikační logika
- **View** = zobrazení dat
- **Controller** = zpracování vstupů
- Web varianta: nový View (HTML) generován pro každý request; controller informuje view o změnách (ne model)
- SPA/AJAX: controller zajišťuje vstup, view pozoruje model a aktualizuje se

**Model-View-Presenter (MVP)**
- Rozbíjí vazbu mezi Modelem a View
- Presenter jako prostředník mezi View a Modelem
- View se skládá z widgetů, každý widget má vlastního Presentera

**Model-View-ViewModel (MVVM)**
- ViewModel poskytuje data a příkazy (commands) pro View
- DataBinding a notifikace: View se aktualizuje při změně ve ViewModelu
- ViewModel může být technologicky nezávislý – pomáhá realizovat Clean Architecture na prezentační vrstvě

**Srovnání komunikace (stručně)**
- **MVC**: Controller zpracovává vstup; View pozoruje Model
- **MVP**: Widgety posílají vstup Presenterům; Presenter aktualizuje View
- **MVVM**: Akce ve View mapovány na příkazy ve ViewModelu; View sleduje ViewModel

**Důležitá pravidla a doporučení**
- Oddělte prezentační logiku od aplikační logiky
- Nezatěžujte se terminologií – existují různé varianty vzorů
- Řiďte se best practices pro zvolenou technologii a interními pravidly týmu
- Neaplikujte vzor jen proto, že je populární – zvažte nejlepší řešení pro konkrétní cíl

## Cross-cutting concerns (průřezové aspekty)

Koncept
- **Funkčnost napříč vrstvami** (presentation, application, data)
- Příklady: **bezpečnost (autorizace)**, **logování**, **transakce**

**Problém při naivní implementaci**
- Závislosti rozptýlené ve všech vrstvách
	- Nákladné změny
	- Kód znepřehledněn ne-souvisejícím kódem
	- Obtížné testování

### Klíčové průřezové aspekty

**Security (autorizace)**
- **Presentation layer** – rozhoduje, zda uživatel vidí konkrétní stránku/view
- **Application layer** – rozhoduje, zda může uživatel zavolat konkrétní akci / číst data

**Logging (logování)**
- Typy: **technické/debug logy**, **audit logy**
- Potřeba: sledovat, co aplikace/uživatel dělá napříč vrstvami

**Transactions (transakce)**
- Používají se v application a data layer pro zajištění **atomicity** akcí

### Přístupy k řešení

#### 1) API dependency and configuration

- Princip: závislost na **rozhraní (interface)**, ne na implementaci
- Použití: logging facades (např. SLF4J)
- Výhody:
	- Volání API odkudkoli v kódu
	- Změna implementace = výměna knihovny + konfigurace
	- Aplikační kód se nemění

#### 2) Aspect-Oriented Programming (AOP)

Co je aspekt
- Modul obsahující kód, který by jinak byl duplicitně v mnoha třídách
- AOP zajišťuje spuštění aspektu při volání specifických metod nebo za určitých podmínek

Příklady použití aspektů
- Logging aspekt: loguje timestamp, uživatele, metodu/třídu, vstupní parametry
- Security aspekt: kontroluje autorizaci před voláním metod business vrstvy

Terminologie
- **Join Point** – místo v provádění programu, kde se spouští průřezový kód (obvykle vykonání metody)
- **Pointcut** – predikát určující, zda se akce provede v daném join pointu (např. `execution(* UserManager.add*(..))`)
- **Advice** – akce prováděná aspektem; typy: **Before**, **After** (returning, throwing), **Around**
- **Weaving** – proces propojení aspektů s cílovým kódem

**Typy weavingu**

- **Compile-time weaving**
	- Realizováno vlastním kompilátorem; vytváří modifikované třídy
	- Nevýhody: potřeba custom compileru, potíže s debuggingem

- **Load-time weaving**
	- Realizováno custom class loaderem; upravuje binárky před načtením
	- Nevýhody: potřeba custom class loaderu, potíže s debuggingem

- **Run-time weaving**
	- Realizováno vytvářením proxy objektů (subclassing)
	- Výhody: originální třídy zůstávají nezměněné za běhu
	- Nevýhody: paměťová náročnost; obtížné použít pointcut na privátní metody
